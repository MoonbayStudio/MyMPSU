# Участие в разработке MyMPSU

Спасибо за желание развивать MyMPSU. Участвовать можно двумя способами:

1. предложить изменение в общий репозиторий через Pull Request;
2. создать самостоятельный проект на основе MyMPSU и развивать его отдельно.

## Fork, branch и Pull Request — в чём разница

- **Fork** — ваша копия репозитория в собственном аккаунте или организации
  GitHub. Он нужен, если у вас нет права записи в `MoonbayStudio/MyMPSU` или вы
  хотите развивать отдельную версию.
- **Branch** — отдельная линия изменений внутри репозитория. Участники команды с
  правом записи могут создавать ветки непосредственно в основном репозитории.
- **Pull Request (PR)** — предложение объединить изменения из вашей ветки или
  fork с веткой `main` исходного проекта.

Не работайте напрямую в `main`. Для каждой задачи создавайте отдельную короткую
ветку: `feature/...`, `fix/...`, `docs/...` или `refactor/...`.

## Как предложить изменение через fork

1. Нажмите **Fork** на странице
   <https://github.com/MoonbayStudio/MyMPSU>.
2. Клонируйте свою копию и добавьте исходный проект как `upstream`:

```bash
git clone https://github.com/YOUR-ACCOUNT/MyMPSU.git
cd MyMPSU
git remote add upstream https://github.com/MoonbayStudio/MyMPSU.git
```

3. Перед началом работы синхронизируйтесь и создайте ветку:

```bash
git fetch upstream
git switch main
git merge --ff-only upstream/main
git switch -c feature/short-description
```

4. Внесите изменения, выполните проверки и создайте содержательный коммит:

```bash
pytest
git add <изменённые-файлы>
git commit -m "Кратко описать изменение"
git push -u origin feature/short-description
```

5. На GitHub нажмите **Compare & pull request**. В качестве base выберите
   `MoonbayStudio/MyMPSU:main`, а в качестве head — ветку своего fork.
6. Опишите цель, поведение для пользователей, способ проверки и известные
   ограничения. Один PR должен решать одну понятную задачу.

## Работа участника основной команды

Если у вас есть доступ на запись, fork не обязателен:

```bash
git clone https://github.com/MoonbayStudio/MyMPSU.git
cd MyMPSU
git switch -c fix/short-description
# изменения и проверки
git push -u origin fix/short-description
```

После этого откройте Pull Request в `main`. Ветки позволяют обсуждать и
проверять изменения до попадания в стабильную версию. Авторство коммитов и PR
сохраняется в истории GitHub.

## Требования к изменениям

- не добавляйте `.env`, пароли, токены, ключи подписи и дампы БД;
- не включайте персональные данные пользователей в тесты, issues и PR;
- обновляйте документацию при изменении запуска или конфигурации;
- запускайте backend-тесты и подходящую сборку мобильного клиента;
- сохраняйте обратную совместимость API либо явно описывайте нарушение;
- используйте собственные домены, OAuth-приложения и signing identifiers в
  самостоятельных развёртываниях.

Отправляя Pull Request, вы предлагаете свой вклад для включения в проект на
условиях Apache License 2.0, как описано в разделе о Contributions самой
лицензии.

## Как указывать исходный проект

Fork на GitHub автоматически связан с исходным репозиторием. Дополнительная
пометка в названии каждой ветки не нужна: авторство видно по коммитам и PR.

Если вы распространяете отдельный проект или сборку на основе MyMPSU:

- сохраните копию файла `LICENSE`;
- сохраните относящиеся к проекту сведения из `NOTICE`;
- отметьте файлы, которые вы существенно изменили;
- не заявляйте, что ваша версия является официальной или поддерживается
  Moonbay Studio без отдельного разрешения;
- добавьте заметный credit в README или раздел «О приложении».

Рекомендуемый текст:

```md
Основано на кодовой базе Moonbay Studio,
первоначально разработанной Nicolas Forest / Moonbay Studio.
Проект распространяется по лицензии Apache License 2.0.
Эта версия является самостоятельной модификацией и не считается официальной,
если не указано обратное.
```

Вы можете добавить рядом список собственных авторов и описание внесённых
изменений. Требование сохранить лицензионные сведения не означает, что
самостоятельные улучшения обязательно нужно отдавать обратно, однако полезные
изменения приветствуются в виде Pull Request.

## Обсуждение крупных изменений

Перед большой переработкой архитектуры, схемы БД, авторизации или публичного API
сначала создайте GitHub Issue. Опишите проблему, предлагаемое решение, миграцию
и влияние на существующие мобильные приложения. Это уменьшит риск выполнить
большую работу, которая не сможет быть объединена.
